## Database, storage and recovery

The existing backup_db command creates compressed pg_dump output or falls back to Django dumpdata, records SHA-256 and table counts, and applies retention pruning. It was **not executed** on institutional data. An existing backup file is not proof of recoverability. The fallback is not a substitute for full PostgreSQL disaster recovery, roles or point-in-time recovery.

Before production, assign an owner and approved RPO/RTO; arrange encrypted off-host backups and protected retention, PostgreSQL roles/schema/data and WAL/PITR if required, consistent evidence/report storage backups, object versioning, signing/secret recovery, and alerts for missed backups. Restore a selected backup plus media to a separate disposable environment, validate checksums/counts/foreign keys and authorized file access, record restoration duration, then obtain recovery acceptance. Never test a restore against the institutional database. Review pruning scope before scheduling backup_db.
